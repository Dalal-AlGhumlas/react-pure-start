# Configuration and launch checklist

## Connect the correct Supabase project

The only project reference committed before this audit was `rhiyfptvvhfhbolxegwy` in `supabase/config.toml`. That file configures the CLI; it does not connect the running website and does not prove that it is the new `law-club-sponsorship` project. Compare the reference in the dashboard before changing it. No live project keys or database connection were supplied for this audit.

Configure these in the application's hosting environment (and `.env.local` for local development):

| Variable                        | Value and visibility                                                               |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| `VITE_SUPABASE_URL`             | URL of the intended project; public, used by admin sign-in                         |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Publishable/anon key of that project; public                                       |
| `SUPABASE_URL`                  | The same project URL, server-side                                                  |
| `SUPABASE_PUBLISHABLE_KEY`      | The same publishable/anon key, used with the admin's user token                    |
| `SUPABASE_SERVICE_ROLE_KEY`     | Service-role JWT or secret key, **server only**; never use a `VITE_` prefix        |
| `VITE_CONTACT_EMAIL`            | Optional override; defaults to the owner-confirmed `Development.lawclub@gmail.com` |

The standard `SUPABASE_ANON_KEY` / `VITE_SUPABASE_ANON_KEY` names are accepted as aliases for the public key. A missing browser public key no longer prevents an anonymous sponsor from submitting through a correctly configured server. The server URL can fall back to `VITE_SUPABASE_URL`; providing explicit matching values remains preferable.

Public `VITE_` values are build-time configuration. Rebuild/redeploy after changing them. Do not paste server secrets into source code, GitHub issues, or public chat messages. Check actual server configuration through the hosting provider's private environment-variable interface.

Run `npm run check:supabase` after configuration. It checks expected columns with the server key and performs an anonymous read check without displaying contact data. An empty result alone cannot prove RLS on an empty table; inspect policies as well.

## Existing database

The user reports already running `drizzle/migrations/0000_create_sponsorship_requests_and_roles.sql`. Do **not** run it a second time: it is the original creation migration, not an idempotent repair script. No migration was changed or executed during this audit.

Confirm in the existing project:

- `sponsorship_requests`, `user_roles`, and `reference_counters` exist with RLS enabled.
- Anonymous users have no sponsorship request read/update policy.
- Only the `admin` role has the existing request SELECT/UPDATE policies.
- Both `trg_set_reference_number` and `trg_touch_sponsorship_requests` triggers exist.
- `status` defaults to `new` and `reference_number` is generated by the trigger.

Useful read-only SQL (no request/contact data):

```sql
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname = 'public'
  and tablename in ('sponsorship_requests', 'user_roles', 'reference_counters');

select relname, relrowsecurity
from pg_class
where oid in ('public.sponsorship_requests'::regclass,
              'public.user_roles'::regclass,
              'public.reference_counters'::regclass);

select trigger_name, event_manipulation, action_statement
from information_schema.triggers
where event_object_schema = 'public'
  and event_object_table = 'sponsorship_requests';
```

## Provision the first administrator

Use the intended Supabase project's Authentication area to create/invite the chosen club administrator and set their password through the provider's secure flow. Copy that user's UUID, then run this once through the SQL Editor with an authorized database account:

```sql
insert into public.user_roles (user_id, role)
values ('REPLACE_WITH_THE_AUTH_USER_UUID'::uuid, 'admin')
on conflict (user_id, role) do nothing;
```

Open `/admin` and sign in. There is intentionally no public admin signup or self-grant path. A regular authenticated user sees access denied. Server handlers verify the identity with Supabase Auth, verify `user_roles`, and query with the user's JWT so RLS still applies. The service-role client is used only for validated public submissions.
